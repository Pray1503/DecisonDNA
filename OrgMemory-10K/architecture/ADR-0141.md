# ADR-0141: Adopt PostgreSQL for fusionerp-core database storage

* **Status:** Accepted
* **Date:** 2022-07-21
* **Related Project:** PRJ-017
* **Owner:** EMP-219
* **Complexity:** Low
* **Priority:** Low
* **Tags:** database, storage, backend

## Context
Our current database strategy for fusionerp-core is experiencing scalability limitations under peak loads. We need a solution that can handle high throughput, support strong consistency, and scale horizontally.

## Problem
High read/write latency during peak traffic periods resulting in database connection pools exhausting, causing intermittent errors in downstream services.

## Alternatives Considered
1. Scale vertical resources on existing systems.
2. Implement a distributed cache layer (e.g. Redis) as a buffer.
3. Migrate to a multi-master distributed DB like PostgreSQL.

## Decision
Migrate the primary storage of fusionerp-core to PostgreSQL to leverage its native scaling and high availability features.

## Rationale
We chose PostgreSQL because of its robust clustering capabilities, low latency reads, and strong developer familiarity. It provides the required performance profile and matches our tech stack.

## Consequences
Developers must learn PostgreSQL-specific query optimization. We must set up migration scripts and operational monitoring for the new clusters.

## Expected Benefits
Reduced query latency by 50%, elimination of connection pool exhaustion incidents, and support for 5x current transaction volume.

## Potential Risks
Complexity of live migration, operational overhead of maintaining clusters, and potential data format conversion issues during the transition.
