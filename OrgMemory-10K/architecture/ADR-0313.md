# ADR-0313: Introduce RabbitMQ for decoupled communications in insightcrm-analytics

* **Status:** Accepted
* **Date:** 2024-04-10
* **Related Project:** PRJ-010
* **Owner:** EMP-026
* **Complexity:** High
* **Priority:** Low
* **Tags:** message-queue, architecture, decoupling

## Context
Direct HTTP calls between insightcrm-analytics and other services create hard dependencies. When downstream systems are down, transactions fail immediately, causing poor customer experience.

## Problem
Tight coupling leads to cascading failures across the backend. We need asynchronous messaging to guarantee eventual consistency and fault tolerance.

## Alternatives Considered
1. Keep synchronous REST APIs but increase timeouts and retry limits.
2. Introduce an HTTP webhook callback system.
3. Deploy RabbitMQ as a centralized event broker.

## Decision
Integrate RabbitMQ to enable asynchronous, event-driven communication between insightcrm-analytics and downstream microservices.

## Rationale
By utilizing RabbitMQ, we can queue tasks and process them asynchronously, absorbing sudden traffic spikes without affecting the main API transaction loop.

## Consequences
Requires handling out-of-order execution, ensuring message idempotency in processors, and setting up telemetry for queue lags.

## Expected Benefits
Cascading failures are avoided; service availability increases to 99.99%; peak traffic load is smoothed.

## Potential Risks
Introducing a single point of failure (event broker), message duplication, and increased complexity in tracing requests end-to-end.
